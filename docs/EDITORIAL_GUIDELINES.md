# Open ERC Composition Laboratory (OECL)

# Editorial Guidelines

Version 1.0

---

# Purpose

This document defines the editorial standards of the Open ERC Composition Laboratory (OECL).

Its purpose is to ensure that all documentation, technical papers, research publications, presentations, website content, and future communications consistently represent the identity, governance, architecture, licensing strategy, and long-term scientific vision of the project.

Editorial consistency is considered part of the overall technical quality of OECL.

---

# Project Identity

Always describe OECL as:

> **The Open ERC Composition Laboratory (OECL) is an independent open research project dedicated to deterministic Ethereum protocol composition.**

Do not describe OECL as:

* a tenio.eth product;
* a tenio.eth platform;
* a commercial framework;
* an ERC implementation;
* a blockchain protocol.

OECL is an independent scientific research project.

---

# Maintainer

Always describe tenio.eth as:

> **The Open ERC Composition Laboratory (OECL) is currently maintained by tenio.eth.**

tenio.eth is the current maintainer and steward of the project.

Where applicable, tenio.eth is also the copyright holder of original works created by tenio.eth.

Documentation should never imply that OECL and tenio.eth are the same entity.

---

# Governance

Documentation should consistently distinguish between:

* the project (OECL);
* the current maintainer (tenio.eth);
* governance;
* licensing;
* intellectual property.

OECL maintains its own:

* scientific mission;
* governance principles;
* architectural identity;
* technical direction;
* research objectives.

---

# Research Mission

OECL exists to study deterministic protocol composition.

The project does not promote individual Ethereum standards.

Instead, OECL studies protocol interoperability through reproducible experimentation and accumulated scientific knowledge.

---

# Architectural Language

Documentation should consistently emphasize:

* modular architecture;
* deterministic experimentation;
* reproducible research;
* protocol interoperability;
* accumulated scientific knowledge;
* scientific methodology;
* long-term maintainability.

Avoid marketing language.

Prefer precise, objective, and technically accurate language.

---

# Core and Research

Always distinguish between:

## OECL Core

The public scientific infrastructure of the project.

## OECL Research

The advanced research platform built upon the Core.

Research extends the Core.

Research never replaces the Core.

---

# Licensing and Intellectual Property

Never confuse:

* software licensing;
* copyright ownership;
* contributor licensing;
* intellectual property;
* governance.

Each concept has its own dedicated documentation.

---

# Scientific Tone

Documentation should:

* remain objective;
* avoid exaggerated claims;
* avoid unsupported statements;
* distinguish implemented functionality from future vision;
* describe observable capabilities rather than assumptions;
* prioritize evidence over speculation.

Scientific credibility is always preferred over promotional language.

---

# Long-Term Vision

Documentation should consistently present the intended long-term ecosystem as:

```text
OECL

↓

OECL Core

↓

OECL Research

↓

OECL Enterprise

↓

OECL Cloud
```

This represents an architectural vision rather than a product roadmap.

Documentation should clearly distinguish between:

* implemented functionality;
* planned development;
* long-term architectural vision.

---

# Terminology

Preferred terminology includes:

* research infrastructure;
* deterministic experimentation;
* reproducible research;
* protocol composition;
* protocol interoperability;
* accumulated scientific knowledge;
* scientific methodology;
* modular architecture;
* research platform;
* scientific infrastructure;
* research ecosystem.

Avoid inconsistent terminology across documents.

---

# Documentation Consistency

All official documentation should remain consistent with:

* README.md
* NOTICE
* LICENSE
* GOVERNANCE.md
* ARCHITECTURE.md
* CONTRIBUTING.md
* CLA.md
* IP_POLICY.md
* LICENSING.md

Changes to the project's identity, governance, licensing strategy, or terminology should be reflected consistently across all official documentation.

---

# Code and Documentation Consistency

Documentation should accurately reflect the current state of the implementation.

Implemented features should not be described as future work.

Future capabilities should not be described as implemented functionality.

Documentation and source code should evolve together whenever possible.

---

# Guiding Principle

Every official document should consistently answer the following question:

> **What is the Open ERC Composition Laboratory (OECL)?**

The answer should remain stable regardless of document type, publication date, implementation status, or future organizational evolution.

The identity of OECL is defined by its scientific mission, reproducible methodology, modular architecture, governance principles, and long-term commitment to deterministic Ethereum protocol composition research.
